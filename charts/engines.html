Where each S3 engine tops out

Raw operations against five engine configurations on one 2-core VM with a cloud disk. One engine at a time; the load generator runs on the same VM. Each point is one 6-second run (repeat runs varied about ±10%). Durable means the engine flushed each PUT to disk before acknowledging it.

What it means for the protocol

  • The protocol already gets 70–75% of what the engine can do. On RustFS the protocol-shaped mix tops out at 576/s and s3log-bench reaches 387–435 commands/s. The rest goes to per-effect work: the LIST, the effect PUT, the watermark compare-and-set, replicas reading effects, and commands that die under overload.
  • On durable engines, the disk's flush rate is the limit, not the protocol: one durable create per command. The engines differ in how many creates share a flush. RustFS needs 1.3–1.6 flushes per create, Versity 0.49. The bare disk, creating plain files with fsync from 16 threads, reaches about 2,500/s at 0.3 flushes each, so better batching inside an engine has 1.5–3.7× headroom.
  • Without fsync, CPU is the limit: RustFS creates go from 683/s to 1,676/s, but the protocol mix only from 576 to 725, because the GETs then dominate CPU.
  • Watermark compare-and-set has to stay uncontended. On RustFS, successes fall from 129/s with one racer to 1/s with 64. With 2 producers raising the watermark once per cycle that's fine; dozens of producers racing on it would not be.
  • LIST cost grows with the prefix on every engine except SeaweedFS. At 50,000 objects a 1,000-key page costs RustFS about 118 ms of CPU, against 42 ms at 1,000. Deleting command objects once they're in an effect would keep cmd/ small.
  • Measured on 2 cores shared with the load generator. GET ceilings with the whole box would be about 6,900/s (RustFS), 6,250/s (Versity), 4,500/s (silo) and 3,400/s (SeaweedFS). Lock contention is inferred from behaviour, not profiled; RustFS's is confirmed by its own 503 namespace_lock_timeout responses.
