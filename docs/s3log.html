s3log

A command queue and effect log kept entirely in one S3 bucket.

What it's for

A database whose only durable state is two logs in an S3 bucket: a command log and an effect log. Clients submit commands (transactions). Commands take effect in one order that everyone agrees on; no command may run twice, and every command a client was told is accepted must run. Clients learn each command's result.

There is no server to coordinate, and no locks. Any number of writers and producers work at once, and any of them may stop at any time.

How it works

  • Writers put each command in the bucket as its own object, cmd/<name>. The name is a UUIDv7, so names sort by time.
  • The watermark is one object holding a name: commands up to it are closed. Producers raise it to now − lag, leaving in-flight PUTs time to land. A writer whose name is still above the watermark after its PUT is told acked: its command will run.
  • Producers take the closed commands not yet executed, in name order, execute them, and publish the results as the next effect: fx/a1, fx/a2, … The PUT is create-only (If-None-Match: *), so the first producer to write effect n wins. There is one history.
  • Readers read the effect log in order. An effect holds its commands' results and the changes they made, so reading it executes nothing. That is how clients get results.

    What if things go wrong?

    • A slow PUT lands after the watermark passed its name: the writer is told unknown. The effects later say whether it ran.
    • A command that lands behind the latest effect's last is never listed: its outcome is dead. Its writer was told unknown, never acked.
    • Two producers race for fx/<n>: one gets 412, discards its work and applies the winner's effect. Same for the watermark: the CAS loser reads it.
    • A producer crashes: all state is in the bucket. Any other producer carries on from the effects.

    KeyHoldsWritten
    cmd/<name>One command. <name>: a UUIDv7.Once, by its writer, If-None-Match: *. Never retried.
    watermarkA command name; names up to it are closed.By producers, If-Match: <etag>, to the UUIDv7 bound for now − lag. Only rises.
    fx/<n>Effect n: last (greatest name it covers) and the commands it ran, in order, with results.By producers, If-None-Match: *. First writer wins.

    Effect keys: n in base62 (0-9A-Za-z) after a letter giving the digit count, so key order is numeric order: a1…az (1–61), b10 (62), …

    Writer

    1. PUT cmd/<new UUIDv7>, If-None-Match: *. Error: unknown.
    2. GET watermark. Name above it: acked. Else unknown.

    Reader

    1. GET fx/<next> until 404; apply each effect's changes and hand out its results.
    2. Outcome: ran if an effect contains the name; dead if an effect's last passed it without it.

    Producer cycle

    1. Catch up: read fx/<next> until 404.
    2. Raise the watermark (CAS); if that fails, GET it.
    3. LIST cmd/ after the latest last, up to the watermark (and a batch cap).
    4. None: wait, repeat. Else GET and execute them in name order.
    5. PUT fx/<next>, If-None-Match: *. 412: apply the winner's.

    Guarantees

    • At most once: one fx/<n> per n, each covering only names after the previous last.
    • Acked commands are never skipped: the writer's PUT landed before it saw the watermark below its name. A producer listing past that name read a higher watermark, so later, so its LIST includes the PUT.
    • Acked commands eventually run, as long as the watermark keeps rising and one producer keeps working.

    S3 assumptions

    • Conditional PUTs on one key are atomic: one create-only PUT wins; If-Match loses no update.
    • Reads and writes of one key are linearizable (AWS documents read-after-write; linearizability during an in-flight write is assumed).
    • A LIST started after a PUT returned includes it, in key order.
